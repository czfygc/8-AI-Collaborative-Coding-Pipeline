# TITAN 疑难 Bug 诊断

阶段化纪律。跳过任何阶段都要明确说明理由。**没有红色反馈回路，就不许进入假设阶段**——直接读代码猜原因是本技能要防的头号失败模式。

来源：改写自 mattpocock/skills 的 `diagnosing-bugs`（MIT, Copyright (c) 2026 Matt Pocock），接入 TITAN 的 M1-M7 与输出沙箱。

## 与 TITAN 流程的分工

| 事项 | 归属 |
|---|---|
| 任务状态、谁在修 | 台账（M1）；开工前确认目标文件无他人 `in_progress` |
| 大日志/大输出怎么读 | T-145 沙箱：`node orchestrator/sandbox.mjs file <日志>`，只读摘要，细节用 `search` |
| 谁验收 | M2：修的人不许自己验收，交给非作者客户端 |
| 密钥 | M5/M7：输出、截图、日志一律先脱敏，密钥永不进命令行 |

## 第 0 步：脱敏

展示命令、输出、抓包前，先替换密钥为 `<REDACTED>`。认证信息放环境变量，不写进要展示的文本。只引用携带信号的那几行。
脱敏后信息不足以判断时，直说并向用户要补充，不要脑补。

## 第 1 步：造反馈回路（本技能的核心）

一切后续都是机械动作。只要有一个**对这个 bug 会变红**的紧回路，原因迟早浮出来；没有回路，盯着代码看再久也没用。在这里投入不成比例的精力。

构造顺序（从前往后试）：

1. 失败测试：单元 / 集成 / 端到端，选能触达 bug 的接缝。
2. HTTP 脚本：curl 打本地服务，断言状态与响应体。
3. CLI + fixture：固定输入，stdout 与已知良好快照 diff。
4. 无头浏览器：Playwright 驱动 UI，断言 DOM / console / network。
5. 回放抓包：把真实请求/事件日志落盘，在隔离环境重放。
6. 一次性最小系统：只拉起复现所需的一个服务或一个函数调用。
7. 属性/模糊测试：偶发错误输出时，跑 1000 个随机输入找失败模式。
8. 二分台架：bug 出现在两个已知状态之间时，自动化"启动 X → 检查"，交给 `git bisect run`。
9. 差分回路：同一输入分别喂新旧版本/两种配置，diff 输出。
10. 人工回路：最后手段。用脚本驱动人点击（提示词写清每步），把人的输出再喂回回路。

### 收紧回路

把回路当产品打磨：更快（缓存准备、缩小范围）、信号更锐（断言具体症状，不是"没崩"）、更确定（钉死时间、播种随机、隔离文件系统、冻结网络）。
30 秒还飘的回路约等于没有；2 秒确定的回路才是调试超能力。

### 非确定性 bug

目标不是干净复现，而是**提高复现率**：循环触发 100 次、并行、加压、缩小时间窗、注入延迟。50% 可调，1% 不可调——先把复现率抬起来。

### 真的造不出回路

停下来明说，列出试过的方法，向用户要：(a) 能复现的环境访问权；(b) 脱敏抓包（HAR/日志/core dump/带时间戳录屏）；(c) 临时加生产探针的授权。**没有回路不许猜。**

### 本阶段完成判据

用**一条命令**（脚本路径/测试调用/curl），**已经至少跑过一次**（贴出调用与输出，脱敏），且满足：

- [ ] 会红：驱动真实 bug 路径，断言用户描述的**那个**症状
- [ ] 确定：每次同一结论（偶发 bug：复现率已钉到可调）
- [ ] 快：秒级，不是分钟级
- [ ] 可无人值守：不需要人点

## 第 2 步：复现 + 最小化

- 回路变红，且是**用户说的那个**失败（不是旁边另一个失败）。
- 多次运行可复现（偶发 bug：复现率足够高）。
- 记下确切症状（报错原文、错误输出、耗时），供后续验证修复。

**最小化**：一次砍一个输入/调用方/配置/步骤，每砍一刀重跑回路，只保留对失败有支撑作用的元素。完成判据：去掉任何剩余元素都会让回路变绿。
没复现、没最小化，不要进下一阶段。

## 第 3 步：假设

先写 **3-5 条排序假设**，再测。单假设会锚死在第一个看起来合理的想法上。

每条必须可证伪，写成预测：
> 如果 <X> 是原因，那么 <改 Y> 会让 bug 消失 / <改 Z> 会让它更糟。

写不出预测的假设是感觉，丢掉或写锐。
**把排序后的清单给用户看**（M6：大白话），他常有领域信息能瞬间重排（"我们刚发了 #3 相关改动"）。用户不在场就按自己的排序继续，不阻塞。

## 第 4 步：插桩

每个探针必须对应第 3 步的一条预测。**一次只改一个变量。**

优先级：
1. 调试器 / REPL 检查（环境支持时）——一个断点胜过十条日志。
2. 能区分假设的边界日志。
3. 禁止"全量打日志再 grep"。

**调试日志统一加唯一前缀**，如 `[DEBUG-a4f2]`，收尾一条 grep 全部清掉；没前缀的日志会活下来。

**性能分支**：性能回归通常不吃日志。先建基线测量（计时台架 / `performance.now()` / profiler / 查询计划），再二分。先测量，后修复。

## 第 5 步：修复 + 回归测试

**先写回归测试，再修**——前提是存在**正确接缝**：测试要能在真实调用形态下复现 bug 模式。只有浅接缝（单调用方、跑不出触发链的单元测试）时，写在那里会给假信心。

- 有正确接缝：最小复现转成失败测试 → 看它红（若靠改代码/夹具强制红，先和干净副本 diff 证明改动生效）→ 修复 → 看它绿 → 拿第 1 步的原始场景再跑一遍。
- 没有正确接缝：**这本身就是发现**。记录下来，作为架构问题交给 code-review / 后续任务。

TITAN 附加：回归测试须登记 `orchestrator/test/SUITES.md`，证据（红/绿输出）落 `archive/evidence/T-xx/`。

## 第 6 步：清理（宣布完成前必做）

- [ ] 原始复现不再出现（重跑第 1 步回路）
- [ ] 回归测试通过（或"无正确接缝"已记录）
- [ ] 所有 `[DEBUG-...]` 探针已删（grep 前缀确认）
- [ ] 一次性脚本/原型已删（M2：`tmp/` 与 `_probe_*` 会话结束前清干净）
- [ ] 根因写进提交信息与台账证据，让下一个调试者少走弯路
- [ ] 台账状态推进并提交；修复由非作者客户端复核（M2）

# TITAN 需求盘问（Grilling）

在开工前把设计树问穿。目标不是走流程，而是**不留任何默默假设**。

来源：改写自 mattpocock/skills 的 `grilling`（MIT, Copyright (c) 2026 Matt Pocock），接入 TITAN 的 M1 台账与 M6 交互规则。

## 与 TITAN 流程的分工

| 事项 | 归属 |
|---|---|
| 任务号、状态、谁在做 | 台账（M1）——盘问的产物要落成台账条目或设计文档 |
| 怎么问、问到什么程度 | 本技能 |
| 给用户几个选项、推荐哪个 | M6：2-3 个选项，每个附理由并标推荐 |
| 事实从哪来 | 你的活：先查代码/文档/实测，查不到再问人 |

盘问**不替代** M1：盘问解决"要做成什么样"，台账解决"谁在什么时候做哪一件"。

## 设计树

把要讨论的事画成一棵树：每个决定下面挂着依赖它的决定。

- **前沿（frontier）** = 所有前置条件已定的决定，也就是现在就能问、不用猜答案的问题。
- **一轮 = 问完整个前沿**。给每个问题编号，并给出你的推荐答案。
- **然后等用户回答**，再重算前沿，进入下一轮。
- 依赖本轮未决问题的问题，属于**后面的轮次**，本轮不问。

## 每轮的格式

```
❓ **Q1 - <问题标题>**：<问题正文，可以多段，可以给多个选项>

➡️ <我的推荐答案 + 一句理由>
```

把那句话写成"用户答'是'就等于接受推荐答案"的形式，降低回答成本。

## 事实是你的活，不是用户的

前沿问题需要环境事实（文件、工具、上游行为）时，自己去查（子代理/命令/搜索），**不要问用户你本可以查到的东西**。
非阻塞原则：正在跑的探查算"未定前置"，只有它下游的问题要等；本轮其余问题照问。

**决定是用户的**：把每个决定摆给他，等回答。不要把"我替你决定了"混进推荐里。

## TITAN 适配

1. **先看台账**：同类任务是否已存在（`todo`/`claimed`/`in_progress`）。已有就基于它盘问，别另起炉灶。
2. **别撞单**：盘问结果涉及别人 `in_progress` 的文件时，先提出协调方案（等/换/拆），不硬上。
3. **大白话**：用户不写代码。问题用业务语言，技术词第一次出现要解释；不要堆术语（M6）。
4. **矛盾主动提示**：用户前后要求冲突时，指出冲突点 + 2-3 个处理选项 + 推荐，不默默选一个执行（M6）。
5. **落盘**：盘问出的决定写进 `design-specs/` 文档或台账 `description`；只在对话里说过等于没说过。
6. **结束才动工**：前沿清空且用户确认"理解一致"之前，不开始改代码。

## 什么时候算完

前沿为空：每条分支都走过了，没有任何东西被默默假设。
此时输出一份"已定决定清单"（每条一行）+ "仍未定/超出范围"清单，请用户确认。确认后才进入 M1 认领与实施。

## 反模式

- 一次只问一个问题、挤牙膏式往返 → 应该整轮前沿一起问。
- 问用户"你的 token 在哪""某个文件写了什么" → 自己能查的事实不要问。
- 用户答完不重算前沿，照着旧清单继续 → 答案会改变树形，必须重算。
- 把推荐答案写成既成事实，用户没答就开工 → 决定权在用户。
- 盘问变成无边界闲聊 → 前沿清空即停；继续问是浪费。
